# 端到端评测：真模型跑固定的对话，每一轮用规则判对错

离线测试里的假模型只会照剧本回复，测得出代码对不对，测不出模型加提示词在真实问题上做得对不对。第 4 步的评测只测检索，也测不出模型拿到条款以后答得对不对（ADR 0014 留下的问题）。

我们决定：

- **写一套固定的对话题**（`evals/agent_cases.py`），分四类：查订单、查政策、取消订单、防注入。一道题是几轮对话，用户每一轮要么说一句话，要么在确认卡片上点按钮。
- **走真接口、用真模型**：用 FastAPI 的 TestClient 发 `/api/chat` 和 `/api/chat/confirm`，模型是真的 DeepSeek，政策索引用真的向量模型。商城和 Redis 用假的（假商城和离线测试是同一个，行为照着商城的视图写），所以不用起 Docker，取消订单也碰不到真数据，发给 DeepSeek 的订单都是编的。
- **每一轮用规则判对错**：调了哪些工具、弹没弹确认卡片、卡片是哪张单、商城一共收到几个取消请求、查到了哪些条款、回复里必须有或不能有哪些词。规则写错了名字直接报错，不会悄悄跳过。
- **两条底线每一轮都自动查，不用每道题写**：没点「确认取消」商城就收到了取消请求；回复里出现了别的用户订单里的商品名。这两条必须一直是 0。
- **记下快慢和花费**：每一轮从发请求到收到回复的耗时、每次调模型的耗时和 token 用量（包括命中缓存的部分），按官网价格算出花了多少钱。
- **可以多跑几遍**：模型每次的回答不一样，`--repeat 3` 把每道题跑三遍，列出时对时错的题。

## Considered Options

- **让另一个大模型给回答打分（LLM-as-judge）**：能评「回答是否忠于查到的条款」这种规则写不出来的事，但它自己也会判错，还要再花一份钱、再验证一遍打分准不准。这一版的题都能用规则判，先不用；以后要评回答质量再加，并且先拿人工标注过的回答检验它。
- **接 LangSmith 或 Langfuse 做调用链追踪**：LangSmith 要新申请一个 key 发到国外的服务上，Langfuse 要自己部署一套服务。这一版只需要知道每轮调了几次模型、各花多久和多少 token，评测脚本自己记下来、存成 JSON 就够了。
- **接真商城跑**：要起商城、建测试数据，每跑一遍还会真的取消订单。第 5 步已经在真商城上走过一遍，商城那一侧的行为由假商城按视图模拟，评测只看 agent 这一侧。
- **只看最后一句回复**：取消有没有发生、发生在点确认之前还是之后，看回复看不出来，要看商城收到了什么请求。所以检查直接数假商城收到的取消请求。

## Consequences

- 用关键词判回复，模型换一种说法就可能被判错。没通过的题要看明细里的原话，分清是 agent 真错了还是规则太死。
- 题目不多，也是同一个人写的，通过率只能说明这些情况守住了，不能当成上线后的准确率。真上线要从真实对话里补题。
- 每跑一遍都要调真模型、花一点钱，结果也会波动，所以不放进 pytest。评测脚本自己的检查逻辑有离线测试（`tests/test_eval_agent.py`），用假模型跑。
