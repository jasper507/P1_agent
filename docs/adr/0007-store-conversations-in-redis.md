# 对话存在 Redis，一段对话一个 key，自带过期时间

我们决定：对话存在 agent 自己的 Redis 里，key 是 `conversation:{对话编号}`，值是一段 JSON（所属用户和最近几轮）。每存一轮就重新设置 30 分钟过期，由 Redis 自己删掉过期的对话，不用写清理任务。Redis 连不上时返回 503，不悄悄退回单轮：用户说「第二张呢」，模型手里没有上一轮，只会答非所问。

设计时说的是「代码里留一个存储接口，测试用自己写的内存版」。实际只写了 Redis 一种实现，测试换成 fakeredis（一个在内存里实现 Redis 命令的库）。原因是最容易出错的是锁的语义（`SET NX EX`、`WATCH`），自己写的内存版只能测到自己的理解；fakeredis 实现的是同一组命令，另外还对真实 Redis 跑过一遍同样的检查。

## Considered Options

- **进程内存（一个 dict）**：最简单，但服务一重启对话全丢；开多个 worker 时每个进程各有一份，下一条消息落到别的进程就找不到对话。
- **SQLite**：能持久化，但过期要自己清理，多进程同时写还要处理锁。
- **商城的数据库**：agent 不保存业务数据，也不往商城的库里写东西；商城仓库现在只读。

## Consequences

- 本地开发多了一个依赖，用仓库里的 `compose.yaml` 起，只监听本机。
- Redis 不开持久化，重启会丢掉所有对话。对话 30 分钟就过期，这个损失可以接受。
- Redis 挂了，多轮对话整个不可用（503）。单机 Redis 没有高可用，上线时再考虑托管的 Redis 或主从。
