# MCP 服务：只把三个只读工具和售后政策原文对外，不提供取消订单

客服的工具（查订单、查订单详情、查售后政策）原来只有我们自己的 agent 能用：模型通过 Function Calling 说要调哪个工具，由 agent 在进程里执行。别的 AI 应用（Claude、Cursor 这类 MCP 客户端）想用同一套工具，就得再对接一遍。

我们决定：

- **加一个 MCP 服务**（`app/mcp_server.py`，官方 Python SDK，stdio 方式，由 MCP 客户端拉起）。工具不重写：三个工具都调 `app/tools.py` 里和 agent 同一个 `execute_tool`，参数白名单（`extra="forbid"`）、错误写成中文交还给模型、订单归属由商城判断，这些规矩一条不少。
- **身份**：MCP 服务跑在用户自己的电脑上，一个进程只代表一个人。商城的 sessionid 从环境变量 `P1_SHOP_SESSIONID` 读，第一次调用工具时问商城「这是谁」，和 agent 的登录校验是同一套。没设置或商城不认，工具返回「未登录」，不去猜身份。
- **不提供取消订单**：取消必须用户在页面上点「确认取消」，这个确认（卡片、一次性操作编号、执行前复查）只在 agent 的接口里有。MCP 客户端那边怎么确认、会不会让模型自己点，我们管不了，所以写操作干脆不对外。三个工具都标了 `read_only_hint`。
- **售后政策原文做成资源**（`policy://{doc_id}`）：工具是「让模型去做一件事」，资源是「一份可以直接读的文档」，由客户端决定要不要放进上下文。只认 `policies/` 目录里已有的文件名，不拿传进来的名字去拼路径。

## Considered Options

- **把取消订单也做成 MCP 工具，交给客户端去确认**：MCP 有让服务端向用户发起确认的机制（elicitation），但支不支持、怎么展示取决于客户端；有的客户端还能设成自动同意。取消订单不能指望别人的界面，等以后真要开放，再用 elicitation 并在服务端复查订单状态。
- **MCP 服务直接连数据库查订单**：会绕开商城的所有权校验，等于在 MCP 里重写一遍权限规则。和 agent 一样只走商城的接口。
- **用 HTTP 方式对外（streamable-http）**：要多做一层认证（每个请求是谁），这一版只给本机的客户端用，stdio 就够了。

## Consequences

- agent 和 MCP 服务共用一套工具实现，改工具只改一处。
- 用户要自己从浏览器复制 sessionid 填进 MCP 客户端的配置，过期了要重新填。这是本机单用户工具能接受的做法，不适合多人共用的服务。
- MCP 客户端那边的模型、提示词我们管不了，回答质量没有评测保证；我们保证的是：通过 MCP 拿不到别人的订单，也动不了任何订单。
