# 一轮是加锁和保存的单位

我们决定：同一段对话同时只处理一条消息。开始一轮前用 `SET 锁的key 随机token NX EX 120` 加锁，拿不到就立刻返回 409，不排队等待。一轮完整跑完才保存；模型半路出错返回 502，什么都不存，用户重发即可。一轮最多跑 90 秒，超时返回 504，同样不存。停不下来、给了兜底回复的一轮，只存用户的话和兜底回复，不存中间的工具调用。

锁有三个细节：

- **带过期时间**：进程半路崩了，锁 120 秒后自己消失，对话不会被永远锁住。
- **一轮的时限比锁短**：锁要是在一轮跑完之前过期，下一条消息就能拿到锁，两轮同时跑，后存的会把先存的覆盖掉。所以一轮最多跑 90 秒，留 30 秒余量给保存；配置里写反了，服务直接起不来。
- **只删自己的锁**：释放时先确认锁里还是自己的 token 再删，而且「确认再删」必须是原子的。Redis 文档给的写法是一段 Lua 脚本；我们用 `WATCH` 加事务实现，效果一样（被 WATCH 的 key 在执行前被改过或过期了，事务就不执行），好处是测试用的 fakeredis 不用装 Lua 支持。

## Considered Options

- **不加锁**：用户连点两次发送，两个请求都读到 N 轮历史，各自存成 N+1 轮，后存的覆盖先存的，丢掉一轮。
- **排队等前一条处理完**：请求会挂很久，还要再设等待超时。连点通常是误操作，409 让前端直接禁用发送按钮更简单。
- **进程内的 `asyncio.Lock`**：只管得住一个进程，开多个 worker 就失效。
- **锁续期（后台定时延长锁）**：能让很长的一轮一直持有锁，但多一个后台任务要管。客服一轮超过 90 秒，用户早就不等了，不如直接放弃。
- **每条消息产生就存**：会存下有工具调用、没有工具结果的半轮，下一次发给模型时接口会报错。

## Consequences

- 同一段对话不能同时发两条消息，前端要在等回复时禁用发送按钮。
- 单个 Redis 上的锁，Redis 宕机或主从切换时可能失效。真要严格互斥，需要 Redis 文档说的 fencing token；现在只读，最坏是丢一轮历史，不值得。
