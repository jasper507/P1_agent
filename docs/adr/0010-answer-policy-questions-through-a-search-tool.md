# 售后政策通过检索工具回答，出处由服务端给出，证据不够在代码里拒答

我们决定：查售后政策做成一个工具 `search_policy`，由模型决定什么时候查，而不是每个问题都先检索一遍。系统提示要求：售后问题必须先查，只根据查到的条款回答，在回答里注明出处。接口另外返回这一轮真正查到的条款（`sources`），由服务端在工具执行时记下，不靠模型自己标。向量那一路的最高相似度低于阈值时，工具直接返回「售后政策里没有找到和这个问题相关的规定」，一条条款都不交给模型。

政策本身是我们写的一份示例商城的虚构政策，共五篇：退换货、退款、运费、发票、保修。每篇开头写明是示例，不对应任何真实公司。

## Considered Options

- **每个问题都先检索，把结果塞进提示词**：不会漏查，但用户问订单时也会塞进一堆无关条款，白费 token；也没法和查订单组合，比如先查订单状态，再查退货期限。
- **出处让模型自己写**：模型可能标错，甚至编一个出处。回答里的出处是写给人看的，接口里的 `sources` 才是准的。
- **拒答只靠提示词**：模型手里有几条不相关的条款，还是可能照着编。代码里先挡一道，模型拿不到条款，就没东西可编。
- **用真实公司的售后政策**：有版权和冒充的问题，内容也不受我们控制，评测题不好出。

## Consequences

- 模型可能不查就凭常识回答。提示词要求必须先查，第 7 步的评测要专门测它有没有查。
- 订单数据里没有签收日期，判断「还能不能退」时，提示词要求模型问用户哪天签收的，不自己猜。
- 阈值是在我们自己出的评测题上定的。换了向量模型，或者政策大改，要重新跑评测、重新定阈值。
- 查到的条款作为工具结果存进对话历史，历史会比只查订单时长一些。
