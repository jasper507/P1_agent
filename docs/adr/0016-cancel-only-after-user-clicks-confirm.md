# 取消订单：模型只能提出，用户点了确认才执行

取消是 agent 的第一个写操作。前几步都是查询，模型理解错了顶多答错一句话；取消错了，订单就没了，已付款的还会退款。模型可能把「那张」理解成另一张，用户的话里也可能藏着提示注入。

我们决定：

- **规则照商城的来**：待付款的可以取消，已付款没发货的取消后全额退款；已发货、已完成、已关闭的不能取消；已经取消的不用再取消。agent 先查一次订单，明显不能取消的直接告诉用户原因，不弹确认卡片。但最终以商城的返回为准，比如商城说「支付结果尚未确认」，就把这句话交给模型。
- **确认是一个按钮，不是一句话**：模型调用 `cancel_order` 时不会马上取消。接口返回一张确认卡片，用户点「确认取消」或「不取消」，前端调 `POST /api/chat/confirm`，带上这次操作的编号（`action_id`）。用户在聊天里回一句「好的」不算确认。
- **卡片由服务端生成**：订单号、商品、金额、取消后会怎样，都按商城返回的订单写，不用模型写的字。
- **一次只确认一张**：模型一次要取消两张，第一张出卡片，第二张告诉模型「一次只能取消一张」。
- **等确认时不能发新消息**：同一段对话再发消息返回 409「请先处理上面的确认」。待确认的操作跟对话一起，30 分钟没动静就过期。
- **确认时重新核对**：用户点了确认，先重新查一次订单。状态和卡片上的不一样（比如看卡片时在别的页面付了款），就不取消，告诉用户订单变了。
- **审计日志**：提出时记一行 `cancel_proposed`，用户点了以后记一行 `cancel_decided`，都是 JSON：哪个用户、哪段对话、哪张订单、操作编号、什么时候、点了什么、结果如何。只有前一行没有后一行的，就是用户没点。不记用户的原话和登录凭证。
- **不知道就说不知道**：取消请求发出去了但没等到回复，可能已经取消了，也可能没有。这时结果写「不确定」，请用户过一会儿查订单状态。商城对已经取消的订单再取消一次是安全的（返回原订单，不重复退款），所以用户再试一次也没关系。

## Considered Options

- **用户在聊天里说「确认」就执行**：模型要判断「好的」是不是在回答这个问题、指的是哪一张，判断错了就是误操作。按钮只对应一张订单、一个动作。
- **卡片文字让模型写**：模型可能把金额或订单号写错，用户确认的就不是真实的订单。
- **等确认时来了新消息，当作「不取消」再接着聊**：体验更顺，但要多处理一种分支。和第 3 步「同一对话同时只处理一条」一样用 409 更简单，前端在卡片没处理完时禁用输入框就行。
- **确认时不重新核对**：中间订单变了，用户同意的就不是现在要发生的事。
- **审计写进数据库**：agent 没有自己的数据库，商城的库只读。日志一行一个 JSON，日志系统可以直接收集。

## Consequences

- 重新查订单和真正取消之间还有很短的空档。商城的取消接口没有「只在某个状态下才取消」的参数，这个空档关不掉，只能靠商城自己的行锁保证不会取消两次。
- 前端要画确认卡片、处理 409，并在确认请求里带上 CSRF token（见 ADR 0018）。
- 用户一直不点，断点就留在 SQLite 里，见 ADR 0017。
