# 用 LangGraph 重写 agent 循环，取消订单的确认用 interrupt

取消订单要「跑到一半停下来，等用户点确认，再接着跑」。用户点确认是另一个 HTTP 请求，可能隔几分钟，中间服务还可能重启。第 2 步手写的循环只能在一个请求里从头跑到尾，做不到这一点。

我们决定：把循环改写成 LangGraph 的一张图。

- `model` 和 `tools` 两个节点就是原来的循环：模型提出调用，代码执行，结果交回模型。原来的 74 个测试照样通过，只是给它们配了一个临时的断点文件，工具清单的测试里补上了新工具。
- 模型调用 `cancel_order` 时，`tools` 不执行它，交给三个新节点：`prepare` 查订单、做确认卡片；`confirm` 调 `interrupt()` 停下来；`execute` 在用户点了以后执行。
- LangGraph 恢复时会把停下的节点从头再跑一遍，`interrupt()` 这次直接返回用户的选择。所以 `confirm` 节点在 `interrupt()` 之前什么都不做，查订单、取消订单都放在别的节点里。
- 调模型还用我们自己的 `AsyncOpenAI` 客户端，消息还是原来的 dict 格式，没有换成 LangChain 的模型类和消息类。存进 Redis 的历史格式不变，假模型的测试也不用改。
- 连接池、登录凭证这些按请求变化的东西，通过 LangGraph 的 runtime context 传给节点，不放进图的状态：状态要存盘，凭证不能存。

## Considered Options

- **继续手写**：把「停在哪、等谁点」存进 Redis，确认时自己把循环接上。几十行就能做，但等于自己重写一遍 checkpoint 和恢复，还要自己处理恢复时重复执行的问题。LangGraph 已经把这些做好了，而且它是现在招聘要求里最常出现的 agent 框架。
- **LangChain 的 `create_agent` 加人工确认中间件**：几行就能有「调用工具前先问人」，但卡片内容、确认前重新核对订单、一次只取消一张这些规则都要绕着中间件写，不如自己画图清楚。
- **用 LangChain 的模型类（ChatOpenAI 等）**：多一层封装，消息格式要改，测试要跟着改，换来的东西这一步用不上。

## Consequences

- 多了 langgraph 依赖，它会带上 langchain-core。
- 图的状态只能放能存成 JSON 的东西：消息、卡片、工具调用记录。
- 面试讲法：框架做了什么（存断点、从断点恢复、恢复时重跑节点）我们知道，手写循环也写过；用它是因为这一步真的需要暂停和恢复。
