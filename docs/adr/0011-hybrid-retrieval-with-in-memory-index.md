# 混合检索：按条款切段，本地向量模型加 BM25，按名次合并，启动时建内存索引

> 后来的修改：评测里合并反而丢分，现在默认只用向量，合并留成开关，见 ADR 0013。下面「只用向量」那一条里「精确的词有时排不到前面」是当时的推测，评测里没有出现。

我们决定：

- **切段**：一条条款切成一段，每段前面拼上标题路径（比如「《退换货政策》 > 1. 七天无理由退货 > 1.1 适用条件」）一起建索引。条款标题必须以编号开头，编号就是出处的一部分，没有编号启动时直接报错。超过 300 字的条款按句子拆开，拆开的几段出处相同；现在的政策里还没有这么长的条款。
- **向量**：bge-small-zh-v1.5（约 2400 万参数），在本机 CPU 上用 fastembed（ONNX Runtime）跑，不用 PyTorch，也不调在线接口。
- **关键词**：jieba 的搜索引擎模式分词，去掉标点和虚词，补几个词典里没有的电商词（包邮、运费险等），再用 BM25 打分。
- **合并**：两路各取前 10 名，用 RRF 合并（在每一路里排第 r 名得 1/(60+r) 分，加起来排序），取前 4 条交给模型。暂时不加重排模型。
- **拒答看向量那一路的最高相似度**，不看合并后的分数：RRF 分数只反映名次，再不相关的问题也有第 1 名。
- **索引**：服务启动时现建，向量放在 Qdrant 的本地内存模式里，BM25 也在内存里。改了政策要重启服务。代码分成「建」和「查」两块。

## Considered Options

- **按固定长度切（比如每 200 字，重叠 50 字）**：会把一条规定切成两半，出处也对不到条款号。政策本来就是一条一条写的，按条款切最自然。
- **只用向量**：换了说法的问题找得到，但精确的词（增值税专用发票、运费险）有时排不到前面。**只用关键词**：分词对不上就一条都找不到，比如「坏了能修吗」对不上「维修」。两者的数字见 `evals/README.md`。
- **把两路的分数加权相加**：余弦相似度在 0 到 1 之间，BM25 分数没有上限，要先归一化，权重还得调。RRF 只看名次，没有要调的东西。
- **加重排模型（reranker）**：通常能再准一点，但多一个模型、每次多一轮推理。评测说不够再加。
- **在线 embedding 接口（比如硅基流动的 BGE-M3）**：要注册账号、放 key，用户的问题会多发给一家第三方，测试和评测也离不开网络。
- **sentence-transformers 加 PyTorch**：最常见的写法，但 PyTorch 的 Windows 安装包就有 100 多 MB。我们只做推理，不训练，ONNX Runtime 够用，安装包约 15 MB。
- **用 Docker 起 Qdrant 服务，或者复用商城的 Elasticsearch**：几十段政策用不上一个服务；复用 Elasticsearch 还会让两个项目又绑在一起。
- **离线建好索引存到磁盘**：要多一个建索引的脚本，还会出现「政策改了，索引忘了重建」。现在几十段，启动时几秒钟就建完。

## Consequences

- 每次启动都要加载模型、把政策算一遍向量；开多个 worker 时每个进程各建一份。政策多了，就把建索引改成离线脚本、Qdrant 换成服务端，查的那块代码不用动。
- 第一次启动要下载模型（约 90 MB）到 `.cache\fastembed\`。fastembed 下载的是 Qdrant 团队转成 ONNX 格式的 bge-small-zh-v1.5，不是 BAAI 官方仓库里的原始权重。
- jieba 已经几年没有更新，在 Python 3.12 及以上第一次导入时会打印几条 SyntaxWarning，不影响使用。
