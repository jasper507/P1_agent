1. 这一步在故事里的位置

第 2 步让 agent 能安全地读订单，但每句话都是独立的：用户问完「我有哪些订单」，再问「第二张是什么时候下的」，agent 不知道「第二张」指什么。

第 3 步加上多轮对话。难点不在「把历史发给模型」，而在服务端从此有了状态：历史存在哪、属于谁、多久过期，用户连点两次发送会不会丢一轮，跑到一半出错会不会留下半截历史。这和项目一里库存扣减、支付回调要处理的是同一类问题，只是对象从订单换成了对话。

面试时的一句话版本：历史只存在服务端的 Redis 里，前端只带对话编号；对话认的是用户，不是登录会话；同一段对话一次只处理一条消息，一轮完整跑完才保存。

2. 业务流程

场景：小明已经在商城登录，先问「我有哪些订单？」，看完回复，再问「第二张是什么时候下的？」

  1. 浏览器第一句不带对话编号。agent 先认人，和第 2 步完全一样：拿 sessionid 去问商城「这是谁」。
  2. agent 入口没带编号就是新对话，由服务端生成一个随机的对话编号（UUID），先给这段对话加锁：同一段对话同时只处理一条消息。
  3. 模型新对话没有历史，和第 2 步一样调 list_my_orders，查到两张订单，回答小明。
  4. Redis一轮跑完，把这一轮的全部消息（小明的话、工具调用、查询结果、最终回复）连同小明的用户 id 存进去，30 分钟后过期。然后释放锁，回复里带上对话编号。
  5. 浏览器第二句带上这个编号：「第二张是什么时候下的？」
  6. agent 入口加锁，从 Redis 读出这段对话，比对用户 id。不是小明的、已过期的、根本不存在的，一律返回 404，模型不会被调用。
  7. 模型收到系统提示、第一轮的全部消息和这句新问题。上一轮的查询结果里就有第二张订单的下单时间，直接回答，不用再查。如果问的是状态，系统提示要求它重新查，因为状态可能已经变了。
  8. Redis把第二轮追加进去。超过 10 轮就丢掉最老的一整轮，重新开始 30 分钟计时，释放锁。

闭环四句话：历史在服务端，前端改不了（第 4 步）→ 对话认用户，别人拿到编号也读不到（第 6 步）→ 一次只处理一条，不会丢一轮（第 2、6 步的锁）→ 一轮跑完才存，历史里没有半截（第 4、8 步）。

3. 失败的时候用户看到什么

规律和第 2 步一样：在调用模型之前就能判断的问题，直接返回 HTTP 错误；一轮跑到一半失败，什么都不存，锁照样释放，用户重发即可。

情况在哪一层被拦用户最终看到
带了别人的、过期的或不存在的编号读对话时比对用户 id404「对话不存在或已过期」，模型不会被调用
编号格式不对，比如 ../../etc请求校验（编号是 UUID 类型）422
上一条还没处理完，又发一条加锁失败409「上一条还在处理，请稍后再发」
一轮跑到一半，模型服务挂了/api/chat 捕获 APIError502，这一轮不存，锁照样释放
一轮超过 90 秒asyncio.timeout504「这次处理太久了」，这一轮不存
模型一直调工具停不下来agent 循环的 max_steps兜底回复；历史里只存问题和兜底回复
Redis 连不上存储层把 RedisError 转成 503503「对话服务暂时不可用」，加锁就失败，模型不会被调用
模型答完了，存的时候 Redis 断了同上503，这一轮白跑，用户重发
进程处理到一半崩了锁的过期时间这段对话 120 秒内发消息返回 409，之后自动恢复

4. 核心代码

都是节选，删掉了导入和大部分注释。完整代码在 app/ 下。

4.1 一轮的骨架

回答的业务问题：一条消息进来，按什么顺序处理？先加锁，再读历史，再跑 agent，跑完才存。任何一步失败，async with 退出时都会释放锁。

4.2 读要认主人，存要整轮截断

回答的业务问题：谁能读这段对话？历史太长怎么办？一段对话就是 Redis 里的一个 key，值是 {"user_id": ..., "rounds": [...]}。SET 带上 ex，每存一次就重新开始计算过期时间[1]，所以 30 分钟是从最后一条消息算起的。

4.3 对话锁：加锁一条命令，释放只删自己的

回答的业务问题：用户连点两次发送，会不会丢一轮？NX 表示 key 不存在才设置，抢到了返回成功，抢不到返回空[1]。token 是这次加锁生成的随机串，释放时用它认出「这是我加的锁」[2]。

4.4 一轮的时限必须比锁短

回答的业务问题：锁会不会在一轮跑完之前就过期？把这个不变量写进配置校验，配反了服务直接起不来，不靠人记。

4.5 每次都把之前几轮一起发给模型

回答的业务问题：模型怎么「记得」上一句？模型本身不记任何东西，每次请求都要把历史完整发过去。停不下来的一轮只交回问题和兜底回复，中间重复的工具调用不存。

5. 面试题和参考答案

先遮住答案，自己出声答一遍，再展开对照。

状态和存储（两类岗位都会问）

Q1. 多轮对话的历史为什么存在服务端，而不是让前端每次带上来？必考

前端带上来的历史是用户能随便改的输入。用户可以伪造一条「工具结果：订单已发货」，或者一句「客服：已为你确认取消」，模型都会当真。这和第 2 步不让前端传 user_id 是同一个道理：影响 agent 判断的东西，不能来自用户可控的输入。现在工具都是只读的，最多是答错；等到取消订单这种写操作，就成了越权。

代价是服务端有了状态，要选存储、处理过期和并发。这一步其余的设计，都是在还这笔账。

Q2. 为什么选 Redis？进程内存或者数据库为什么不行？必考

对话的特点是：短命（30 分钟没人说话就没用了）、按编号整读整写、丢了可以接受。Redis 正好对得上：按 key 读写，自带过期，不用写清理任务。对话锁也需要一个所有进程都能看到的地方，Redis 一并解决。

进程内存最简单，但服务重启就丢；开多个 worker 时每个进程各有一份，下一条消息落到别的进程就找不到对话。SQLite、MySQL 能持久化，但过期要自己清理，而且这些数据不值得持久化。商城的数据库更不行：agent 不保存业务数据，也不往商城的库里写东西。

Q3. 别人拿到了对话编号会怎样？为什么回 404 不回 403？重新登录还能接着聊吗？

存对话时记下所属用户的 id，每次读之前和当前用户比对，对不上就当它不存在，返回 404，模型根本不会被调用。不回 403，是因为 403 等于承认「这个编号是真的，只是不属于你」；商城对别人的订单也回 404，保持一致。编号是随机 UUID，难猜只是加一层防护，真正的检查是比对用户 id[6]。

对话绑的是用户，不是登录会话。重新登录以后 sessionid 变了，但还是同一个用户，可以接着聊；也不用把会话号这种凭证存进 Redis。

Q4. 用户连点两次发送，会发生什么？必考

如果不加锁：两个请求都读到 N 轮历史，各自跑完，各自存成 N+1 轮，后存的覆盖先存的，丢掉一轮。这是典型的「读、改、写」丢失更新。

所以同一段对话同时只处理一条：开始前加锁，拿不到就立刻返回 409。不排队，是因为排队要让第二个请求挂着等，还得再设一个等待超时；连点通常是误操作，前端在等回复时禁用发送按钮就够了。也不用 asyncio.Lock：它只管得住一个进程，开多个 worker 就失效，锁必须放在所有进程都能看到的 Redis 里。

Q5. Redis 锁具体怎么实现？为什么要随机 token，为什么要过期时间？亮点

加锁是一条命令：SET conversation:{编号}:lock 随机token NX EX 120。NX 表示 key 不存在才设置，已经存在就返回空，判断和设置在一条命令里完成，不会两个请求同时抢到[1]。

过期时间是给崩溃留的后路：进程半路崩了，没机会释放锁，120 秒后锁自己消失，对话不会被永远锁住。token 用来认出「这是我加的锁」，释放时只删 token 对得上的。直接 DEL 会出事：我这一轮跑得比锁还久，锁过期后被下一条消息拿走，我结束时一个 DEL 就把别人的锁删了。Redis 官方文档讲的正是这个场景[2]。

可以主动补一句：Redis 文档在这种单实例写法旁边注明，更推荐 Redlock[1]。Redlock 用多个独立的 Redis 节点，解决单个 Redis 宕机时锁失效的问题。我们的锁只是防用户连点，不保护钱和库存，单个 Redis 够用。

Q6. 如果一轮跑得比锁的过期时间还长，会怎样？你怎么防的？亮点

锁过期后，下一条消息就能拿到锁，两轮同时跑，后存的覆盖先存的，又回到丢失更新。token 只保证不删别人的锁，挡不住这个。

我的做法是保证一轮一定在锁过期之前结束：一轮总时限 90 秒，锁 120 秒，中间留 30 秒给保存；超时返回 504，这一轮不存。这个不变量写在配置校验里，配反了服务起不来。为什么要单独设总时限？模型客户端单次超时 30 秒、失败还会重试 2 次，一轮最多 5 步，不设总时限的话，最坏情况远远超过 120 秒。

其他方案：锁续期，也就是后台定时把锁延长，Java 的 Redisson 叫它「看门狗」，能支持很长的任务，但多一个后台任务要管；客服一轮超过 90 秒用户早就不等了，不如放弃。更严格的是 fencing token：每次加锁拿一个递增的编号，写入时由存储拒绝旧编号。Redis 文档建议耗时长的任务都这样做[2]，我们现在不需要。

Q7. 释放锁为什么必须是原子的？你为什么用 WATCH 而不是 Lua？

释放分两步：读出锁的值，对得上再删。如果这两步之间锁正好过期、被别人拿走，删掉的就是别人的锁，所以「比较再删除」必须是一个不可分割的操作。

Redis 文档给的写法是一段 Lua 脚本，脚本在 Redis 里整体执行[1]。我用的是 WATCH 加事务：先 WATCH 锁的 key，读出来比对，对得上再在事务里删。只要 WATCH 之后这个 key 被改过，包括被 Redis 自己过期删掉，事务就不执行[3][5]。效果一样，选它是因为测试用的 fakeredis 不装额外的 Lua 支持也能跑。

代价是多一次往返，Redis 文档也说同样的事用脚本通常更简单、更快[3]。Redis 8.4 以上可以直接用一条 DELEX key IFEQ token[2]。

Q8. Redis 挂了会怎样？为什么不降级成单轮对话？重启丢数据能接受吗？

加锁是第一个 Redis 操作，连不上就返回 503，模型不会被调用。Redis 连接设了 2 秒超时，不会把请求拖死。如果是模型答完、存的时候断了，也返回 503，这一轮白跑，用户重发。

不降级成单轮，是因为用户以为自己在接着聊：问「第二张呢」时，模型手里没有上一轮，只会答非所问，比明确报错更糟。持久化是故意关掉的：对话 30 分钟就过期，重启丢掉的损失很小。上线要高可用时，换托管的 Redis，或者主从加哨兵。

AI 应用（agent 岗重点）

Q9. 历史里存什么？为什么连工具调用和查询结果一起存？必考

按发给模型的格式整轮原样存：用户的话、模型的工具调用、工具结果、最终回复。只存双方文字的话，用户问「第二张详细说说」，模型手里没有订单号，只能再查一遍，还可能把「第二张」对错。存了查询结果，上一轮查到的订单号和下单时间都还在。

存进去的工具结果是第 2 步做过减法的版本，本来就没有姓名、电话和详细地址，所以历史里也没有。

Q10. 历史越来越长怎么办？为什么按整轮截断，为什么不做摘要？必考

只留最近 10 轮，超过就丢最老的一整轮。必须以轮为单位，是因为 OpenAI 兼容的接口要求每条工具结果前面都有发起它的那条工具调用；按条数截，可能把调用丢了、结果还留着，下一次请求就会报错。这条规则我们还没在 DeepSeek 文档里找到原文，联调时会实测。

摘要能留住更多信息，但每次多调一次模型，多一份延迟和费用，摘要本身也可能出错：把「已取消」概括成「有问题的订单」，后面就全错了。客服问题大多几轮就解决，先用最简单的。代价是 10 轮以前的内容会忘；而且轮数不等于 token 数，一轮里查了很多订单时会很长，以后可以改成按 token 预算截断。

Q11. 历史里的订单状态过时了怎么办？

历史里存的是查询那一刻的状态，20 分钟前查到「已付款」，现在可能已经发货了。所以系统提示要求模型：用户问状态时，即使前面查过，也要重新调用工具。历史用来理解「第二张」指的是哪一张，事实以最新的查询为准。

这只是提示，模型不一定百分之百照做。后面做评测集时，会专门放「查过一次，再问状态」的用例来量。

Q12. 一轮跑到一半出错，历史会变成什么样？停不下来的一轮存什么？

一轮完整跑完才存。模型半路挂了（502）或者超时（504），这一轮什么都不存，锁在 finally 里照样释放，用户重发即可。如果边跑边存，可能存下「有工具调用、没有工具结果」的半轮，之后每次请求都会报错，这段对话就坏了。

到了 max_steps 还停不下来、给了兜底回复的一轮，只存用户的话和兜底回复。中间那几次重复的工具调用没有用，存下来还会占满 10 轮的额度。

Q13. 多轮对话和 Redis 锁是怎么测试的？

单元测试用 fakeredis，它在内存里实现了 Redis 的命令，测试不用起 Redis，跑的是真的存储代码[4]。测试里可以直接看 Redis 里存了什么、模拟 Redis 断开、提前放一把「别人的锁」来测 409 和不误删。没有自己写一个内存版的存储，是因为最容易错的是锁的语义，自己写的假货只能测到自己的理解。

然后做变异测试：故意把代码改坏，比如释放锁不比 token、读对话不比用户 id、不截断、出错不放锁、去掉一轮的时限，一共 9 种，每一种都有测试变红，说明测试真的在测东西。最后对真实的 Redis 跑了一遍同样的加锁、释放和过期检查，确认和 fakeredis 的行为一致。一共 57 个测试。

6. 已知取舍和改进方案

现在的做法代价改进方案
只留最近 10 轮，按轮数截断更早的内容会忘；一轮里查了很多订单时会很长按 token 预算截断；或把老的轮次压成摘要
忙就返回 409，不排队前端要处理 409前端等回复时禁用发送按钮；真有需要再做排队
一轮最多 90 秒，超时放弃极慢的时候用户要重发锁续期加 fencing token，支持更长的一轮

释放锁用 WATCH 事务比 Lua 脚本多一次往返换成 Lua 脚本；Redis 8.4 以上用 DELEX key IFEQ token
对话过期即删没法回看，也没法拿真实对话做评测后面做评测集时，把对话脱敏后归档
