P1_AGENT · 第 0–4 步

P1 客服 Agent 学习手册

这份手册只回答三个问题：这个项目到底解决什么问题；每一步为什么要做、和上一步比变了什么；代码一行一行在干什么。读完你应该能用自己的话把整个项目讲一遍。

先说结论：这个项目解决什么问题

你做了一个电商网站（项目一）。网站上线后，客服每天被问的问题大概就这几类：

我的订单到哪了？
买的 T 恤签收五天了，还能退吗？
买多少钱包邮？
帮我把那张没付款的订单取消掉。

这些问题的答案其实都已经在系统里：订单在数据库里，规则在售后政策里。让人工客服去查、去念，既慢又贵。所以我们想让大模型来当客服。

但直接把大模型接上去会出三种事故，这个项目每一步都是在堵其中一个洞：

看到别人的订单模型根据用户说的「帮我查 u2 的订单」就去查了，泄露隐私。
瞎编政策用户问「降价能退差价吗」，政策里根本没写，模型凭常识编一个「可以」。
乱动订单用户只是问问，模型就把订单取消了；或者重复取消、退两次款。

所以这个项目一句话可以这么说：给自己的电商系统做一个 AI 客服，让它能查订单、答政策、办业务，同时保证它不越权、不编造、不乱操作。技术都是为这三条服务的，不是为了堆名词。

五步的路线（每一步多会一件事、多堵一个洞）

0最小 agent 循环模型自己决定要不要查订单。理解 agent 的原理。 1做成一个网络服务从脚本变成别人能调用的接口，可以离线测试。 2接上真实登录和真实订单堵「看到别人订单」这个洞。 3记住上下文，支持追问「那第二张呢」能接上；多人同时用也不串。 4按售后政策回答（RAG）堵「瞎编政策」这个洞，并用评测数字证明效果。 5+接下来：取消订单要先确认堵「乱动订单」这个洞。
第 0 步

最小 agent 循环：模型自己决定查不查

业务场景：用户问「我有哪些订单？」，模型要知道自己答不出来，得先去查。

我有哪些还没付款的订单？
模型 → 调用 list_my_orders(status="PENDING_PAYMENT")
程序 → 返回 [{"order_id":"A1001","status":"PENDING_PAYMENT","total":"199.00"}]
您有 1 张待付款订单：A1001，金额 199 元。
类比：模型像一个新来的客服，脑子好但不知道店里的数据。工具（Function Calling）就是给他一部内线电话。他自己判断要不要打电话、打给谁、问什么；电话那头（我们的代码）负责真的去查。「agent 循环」就是：他打完电话，听到结果，再决定是继续打还是直接回答客人。
step0/agent.py（核心部分）
def run_agent(user_input, max_steps=5):
    messages = [
        {"role": "system", "content": "你是电商客服。涉及订单信息时必须调用工具查询，不要编造。"},  # ①
        {"role": "user", "content": user_input},
    ]
    for step in range(1, max_steps + 1):                     # ②
        resp = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
        msg = resp.choices[0].message
        messages.append(msg)                                 # ③
        if not msg.tool_calls:                               # ④
            return msg.content
        for call in msg.tool_calls:                          # ⑤
            args = json.loads(call.function.arguments or "{}")
            result = TOOL_MAP[call.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "达到最大步数，停止"
  1. 系统提示：告诉模型它的身份和规矩。注意它只能「劝」模型，管不住模型。
  2. 最多循环 5 次。防止模型一直调工具停不下来，白白花钱。
  3. 模型说的话（包括「我要调哪个工具」）也要放回对话里，下一次它才记得自己刚才干了什么。
  4. 模型没要求调工具，说明它已经可以回答了，循环结束。
  5. 模型要求调工具：我们真的执行这个函数，把结果用 tool_call_id 对上号再交回给模型。

这一步里藏着的一个关键设计

工具 list_my_orders 的参数里只有 status，没有「用户是谁」。用户是谁由代码里的 CURRENT_USER 决定。所以就算用户说「帮我查 u2 的订单」，模型也没有办法把 u2 传进去。这个思路一直用到最后一步。

Function Callingagent 循环步数上限
面试这么说：我先不用框架，手写了一个 agent 循环：模型返回 tool_calls 就执行工具、把结果回填，没有 tool_calls 就结束，并设了步数上限。这样我清楚框架底层在做什么。
第 1 步

做成一个网络服务

业务场景：脚本只能自己在命令行里跑。网站的聊天框要能把用户的话发过来、拿回答案，所以要变成一个 HTTP 接口：POST /api/chat。

第 0 步的问题

  • 只能在命令行跑，网站用不了
  • 测试要真的调 DeepSeek，花钱、慢、结果不稳定
  • 密钥写在代码旁边

第 1 步的改法

  • FastAPI 提供 /api/chat 接口
  • 测试里用「假模型」代替 DeepSeek，不连网、不花钱
  • 配置统一从 .env 读，密钥不进代码库
类比：第 0 步是你在家里给自己做饭；第 1 步是开了一个外卖窗口，别人按固定格式下单（请求体 {"message": ...}），你按固定格式出餐（{"reply": ..., "tool_calls": [...]}）。「假模型」就像试营业时请朋友扮演客人，不用真的进货。
app/main.py（简化，只看骨架）
@app.post("/api/chat", response_model=ChatResponse)     # ①
async def chat(
    body: ChatRequest,                                   # ②
    user: CurrentUser = Depends(get_current_user),       # ③
    llm: AsyncOpenAI = Depends(get_llm),                 # ④
):
    result = await run_agent(llm, message=body.message, ...)
    return ChatResponse(reply=result.reply, tool_calls=result.tool_calls)
  1. 声明一个 POST 接口；response_model 规定返回的格式，多余字段不会漏出去。
  2. ChatRequest 是 Pydantic 模型：message 必须是 1 到 500 个字，不合格 FastAPI 直接回 422，代码里不用手写校验。
  3. Depends 叫「依赖注入」：接口需要「当前用户」，就交给 get_current_user 去算。第 1 步它返回的是假用户，第 2 步换成真登录，接口代码一行不用改。
  4. 模型客户端也是注入进来的。测试时把它换成假模型，这就是「能离线测试」的原因。
FastAPIPydantic 校验依赖注入离线测试
面试这么说：我用 FastAPI 的依赖注入把「当前用户」「模型客户端」都做成可替换的依赖。测试时换成假实现，整个 agent 循环不连网就能测，测试稳定也不花钱。
第 2 步 · 堵「看到别人订单」

接上真实登录和真实订单

业务场景：用户在你的电商网站登录后打开客服，问「我有哪些订单」，看到的必须是他自己的真订单。

帮我查一下订单 0000…0000 的详情（其实是别人的订单）
agent → 以「当前用户」身份问商城：这张订单给我看看
商城 → 404：不是你的订单
查不到这张订单，可能订单号有误，或者它不属于当前账号。

第 1 步的问题

  • 用户是假的，订单是假的
  • agent 自己要管「谁能看什么」，容易写错

第 2 步的改法

  • 浏览器带来的登录凭证（sessionid）原样交给商城验证
  • 查订单也用这个身份，由商城判断订单是不是你的
  • agent 自己不存、不猜任何用户身份
类比：客服 agent 是银行大堂经理，商城是柜台。大堂经理不自己判断你能取多少钱，而是拿着你本人的身份证去柜台办。柜台怎么规定，就怎么办。经理手里没有万能卡，所以就算被人骗，也办不出别人的业务。
app/auth.py：每个请求先确认「你是谁」
async def get_current_user(request, django=Depends(get_django)):
    session_id = request.cookies.get("sessionid", "")           # ①
    if not SESSION_ID_RE.fullmatch(session_id):                  # ②
        raise HTTPException(401, "未登录")
    try:
        me = await django.me(session_id)                         # ③
    except DjangoUnauthorized:
        raise HTTPException(401, "未登录或登录已过期")
    except DjangoError:
        raise HTTPException(502, "电商服务暂时不可用，请稍后再试")   # ④
    return CurrentUser(id=me["id"], username=me["username"], session_id=session_id)
  1. 从浏览器的 cookie 里取出登录凭证。因为 agent 和商城在同一个域名下，用户在商城登录过，这里就能拿到。
  2. 先检查格式（只能是小写字母和数字）。格式都不对就不用去问商城，也防止有人塞换行、分号进去伪造请求头。
  3. 拿着凭证去问商城的 /api/auth/me/：「这个人是谁？」商城说了算。
  4. 商城挂了和用户没登录是两回事，分别回 502 和 401，前端才能给出正确提示。
app/tools.py：模型能传的参数被锁死
class GetOrderDetailArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")    # ①
    order_id: UUID                               # ②

def summarize_order(order):                      # ③
    return {"order_id": order["public_id"], "status": order["status"],
            "total": order["total"], "items": [...]}
  1. extra="forbid"：模型如果多传一个 user_id，直接算参数错误。模型想越权，连门都没有。
  2. 订单号必须是合法的 UUID 才会被拼进网址，防止拼出奇怪的路径。
  3. 发给模型之前去掉收件人姓名、电话、详细地址。模型服务在第三方，用不上的个人信息就不发（数据最小化）。

还有一个容易被忽略的坑：串号

所有用户共用同一个 HTTP 客户端（为了复用连接，更快）。普通客户端会像浏览器一样记住商城返回的 cookie，下一个用户的请求要是忘了带凭证，就会自动带上上一个人的。我们给它配了一个「什么都不存」的 cookie 罐子，彻底杜绝这个问题。

身份透传越权防护参数白名单数据最小化错误分级（401 / 404 / 502）
面试这么说：模型只能决定「查什么」，不能决定「以谁的身份查」。身份来自浏览器的登录凭证，由商城验证；订单归属也由商城判断。工具参数用白名单锁死，模型想传 user_id 都传不进去。
第 3 步

记住上下文，支持追问

业务场景：真实客服对话很少一问一答就结束。

我有哪些订单？
您有两张订单：① T 恤 199 元，已发货；② 耳机 89 元，待付款。
那第二张呢，什么时候过期？
（第 2 步的 agent 不知道「第二张」是哪张，答不上来；第 3 步可以）

第 2 步的问题

  • 每次请求都是全新的，模型不记得上一句
  • 如果让前端把历史传过来，前端可以伪造「客服之前说过可以退」

第 3 步的改法

  • 对话历史存在服务端的 Redis 里，30 分钟过期，最多留 10 轮
  • 每段对话记着属于谁，别人拿到编号也读不了
  • 同一段对话同一时间只处理一条消息（加锁）
类比：Redis 是客服台上的「对话记录本」，每段对话一页，页眉写着客人的名字。别人拿着页码来，名字对不上就当没这页。加锁就像「这页正在写，请稍等」：客人连点两次发送，第二次会被告知「上一条还在处理」，不会两条回答互相覆盖。
app/main.py：一轮对话的完整流程
conversation_id = body.conversation_id or uuid4()                  # ①
async with conversations.lock(conversation_id):                     # ②
    history = [] if body.conversation_id is None else \
        await conversations.load(conversation_id, user.id)          # ③
    async with asyncio.timeout(settings.round_timeout_seconds):     # ④
        result = await run_agent(llm, history=history, message=body.message, ...)
    await conversations.save_round(conversation_id, user.id,
                                   history, result.new_round)       # ⑤
  1. 第一次提问没有编号，服务端生成一个新的，跟着回答一起返回；之后前端每次带上它。
  2. 给这段对话加锁。锁本身有过期时间（120 秒），程序半路崩了，锁也会自己消失，不会把对话永远锁死。
  3. 读历史时同时传入用户 id：对话不属于这个用户，就当它不存在（返回 404，和商城对待别人订单的方式一样）。
  4. 一轮最多跑 90 秒。必须比锁的 120 秒短，否则锁过期了另一条消息进来，两边会同时改同一段历史。
  5. 一轮完整跑完才保存，而且是整轮保存（用户的话 + 工具调用 + 工具结果 + 回答）。跑到一半出错就不存，用户重发即可。

为什么要「整轮」保存和截断？

模型接口有个硬规定：一条「我要调用工具」的消息后面，必须紧跟着对应的工具结果。如果按条数截断，可能把工具结果删了、调用留着，下一轮发给模型就会直接报错。所以历史只按「轮」来留和删。这种「控制发给模型的上下文」的工作，叫上下文工程，是 AI 应用岗常问的内容。

还有一条提示词规则：「之前查到的订单状态可能已经变了，用户问状态时要重新查」。防止模型把 10 分钟前的记忆当成事实。

Redis会话归属分布式锁超时控制上下文工程
面试这么说：对话历史放在服务端 Redis，不信任前端传来的历史。按「轮」保存和截断，保证工具调用和结果总是成对。同一对话用带过期时间的锁串行处理，一轮的超时比锁短，避免锁过期后并发写。
第 4 步 · 堵「瞎编政策」

按售后政策回答（RAG）

业务场景：用户问的是规则，不是订单。答案在售后政策文档里（我们写了 5 份虚构的政策：退换货、退款、运费、发票、保修，一共 49 条条款）。

买的 T 恤签收五天了，还能退吗？
模型 → 调用 search_policy("签收五天还能无理由退货吗")
程序 → 找到《退换货政策》1.1 适用条件：自签收之日起七天内……
可以。签收七天内、吊牌包装完好的商品支持无理由退货（《退换货政策》1.1）。
买完就降价了，能退差价吗？
售后政策里没有关于退差价的规定，建议联系人工客服确认。

第 3 步的问题

  • 模型只能凭「常识」回答政策问题
  • 每家店规则不同，常识答案经常是错的
  • 答错了也没有出处可查

第 4 步的改法

  • 先检索政策条款，再让模型只根据查到的条款回答
  • 回答带出处；接口另外返回真正查到的条款原文
  • 相关度不够就一条都不给，模型手里没有条款，就没法照着编
类比：RAG（检索增强生成）就是「开卷考试」。模型是考生，政策文档是课本。检索是「先翻到相关的那几页」，生成是「照着这几页答题」。拒答阈值就是监考老师：如果翻到的几页明显不相关，干脆不让答，回一句「课本上没写」。

RAG 分三步，对应三个文件

① 切段（app/policy_chunks.py）：按条款切，一条条款一段，并把「《退换货政策》 > 1. 七天无理由退货 > 1.1 适用条件」这样的标题路径拼在正文前面。这样正文里没写「退货」两个字，也能凭标题搜到。条款号同时就是出处。

② 向量化并建索引（app/policy_search.py）：用本机的小模型 bge-small-zh 把每段文字变成一串数字（向量）。意思相近的话，向量也相近。向量存进 Qdrant（在程序内存里运行，不用单独起服务）。服务启动时建一次，现在只要 1.2 秒。

③ 检索并把关：

app/policy_search.py：查的时候
def search(self, query):
    vector_hits = self.vector_search(query)                     # ①
    top_score = vector_hits[0][1] if vector_hits else 0.0
    if top_score < self.min_score:                              # ②
        return SearchResult(chunks=[], top_score=top_score)
    ranking = [i for i, _ in vector_hits]
    if self.hybrid:                                             # ③
        ranking = rrf([ranking, self.keyword_search(query)])
    return SearchResult(chunks=[self.chunks[i] for i in ranking[:self.top_k]],
                        top_score=top_score)                    # ④
  1. 把用户的问题也变成向量，在 Qdrant 里找最像的 10 段，每段带一个相似度（0 到 1，越大越像）。
  2. 第一道关（代码）：最像的那段相似度都低于 0.55，说明政策里大概率没有这方面的规定，一段都不给模型。
  3. 关键词检索（jieba 分词 + BM25）默认关闭，只在配置打开时和向量结果合并。为什么关掉，看下面的评测。
  4. 给模型最相关的 4 段。
app/tools.py：把检索包装成模型能调用的工具
async def search_policy(ctx, args):
    result = await asyncio.to_thread(ctx.policies.search, args.query)   # ①
    if not result.chunks:
        return {"found": False, "message": "售后政策里没有找到和这个问题相关的规定"}
    ctx.sources.extend(result.chunks)                                    # ②
    return {"found": True,
            "clauses": [{"citation": c.citation, "text": c.text} for c in result.chunks]}
  1. 向量模型在 CPU 上算，放到单独的线程里跑，不卡住同时在处理的其他用户。
  2. 真正查到了哪些条款，由代码记下来，接口原样返回给前端。模型在回答里标错了出处，也不影响这份列表。

第二道关（提示词）：系统提示要求「查到的条款如果没回答用户问的事，也要照实说没有规定，不要凭常识补充」。第一道关拦不住的，靠它兜底。

怎么证明它有效：评测

我们准备了 63 道题：51 道政策里有答案（每道标好了正确条款），12 道政策里没有（比如「能分期吗」）。评测不调用大模型，只测检索，所以又快又稳定，改一次参数跑一次就知道变好还是变坏。

指标一：查得准不准（Recall@4）。意思是「正确条款有没有出现在给模型的前 4 段里」。51 道题里有几道命中，就是几除以 51。

只用向量1.00（51 道全中）。现在的默认设置。
只用关键词0.80。关键词只认字面。比如用户说「盒子破了」，政策写的是「外包装破损」，两句话几乎没有相同的词。
两个合并0.96，比只用向量还低。关键词那一路把「快递盒子破了」「发票什么时候开」这两道题的正确条款挤出了前 4。

所以我们根据数据默认只用向量，混合检索留成开关。这是第 4 步面试最值得讲的一段：不是名词越多越好，而是用评测决定要不要。

指标二：该拒的拒没拒。下面这张图里，每个点是一道题，横轴是它和最像那段政策的相似度。绿色是政策里有答案的题（只画了最低的那道），红色是政策里没有的 12 道。竖线是拒答阈值：线左边的会被拒答。

读图：阈值 0.55 时，左边 6 个红点被代码直接拒答；右边 6 个红点（比如「退差价」0.666、「预约周末送货」0.597）放行了，要靠第二道关（提示词）兜底。绿点 0.569 在线右边，说明所有有答案的题一道都没被误拒。

为什么不把线再往右挪？挪到 0.60，红点只剩 1 个漏网，但会误拒 3 道本来有答案的题。客服场景里，「明明有规定却说没有」比「多让模型看一眼」更伤用户，所以选 0.55，再用提示词补漏。

面试这么说：政策问题走 RAG：按条款切分、向量检索、带出处回答。我做了混合检索，但评测显示只用向量 Recall@4 是 1.00、混合反而 0.96，所以默认只用向量。拒答分两道关：相似度低于 0.55 代码直接不给条款；放行的再由提示词要求「条款没回答就说没有」。阈值是用 63 道标注题选出来的。

每个技术解决什么问题

如果面试官问「你为什么用 X」，答案都在下面。答不出「没有它会怎样」的技术，就不该出现在项目里。

Function Calling让模型能「打电话查数据」。没有它：模型只能凭记忆回答订单问题，必然编造。
FastAPI把 agent 变成网站能调用的接口；依赖注入让各部分可替换。没有它：只能命令行跑，也很难离线测试。
Pydantic校验请求和工具参数，extra="forbid" 挡住越权参数。没有它：要手写一堆 if 判断，漏一个就是漏洞。
转发 sessionid复用商城的登录和权限判断。没有它：agent 要自己维护一套权限，两套规则迟早不一致。
Redis存对话历史、给对话加锁、自动过期。没有它：不能追问；或者信任前端传的历史，可被伪造。
向量检索按「意思」找政策条款。没有它：「盒子破了」搜不到「外包装破损」。
BM25 + RRF关键词检索和融合，作为对照实验保留。评测证明它在这份数据上帮倒忙，所以默认关闭。
评测脚本用数字回答「改完变好还是变坏」。没有它：调参数全凭感觉，面试也说不清效果。
假模型 / 假商城测试不连网、不花钱，结果稳定。没有它：每次测试都要起商城、调 DeepSeek，又慢又不可重复。

工程能力体现在哪

  • 安全边界放在代码里，不放在提示词里：身份、权限、拒答第一道关都是代码判断，提示词只做兜底。
  • 失败有分级：未登录 401、不是你的 404、商城或模型挂了 502、超时 504、正在处理 409。前端能给出对的提示，排查也容易。
  • 并发和一致性：对话锁、锁比超时长、整轮保存，这些和你项目一里的库存锁是同一类问题。
  • 用数据做决定：混合检索做了，但评测说不该默认用，就关掉，并写成设计决策记录（ADR 0013）。
  • 可测试：74 个离线测试，加上真实商城和真实模型的联调。

下一步安排

第 5 步：取消订单，先确认再执行（LangGraph）
业务：用户说「帮我取消那张没付款的订单」。
风险：模型理解错了就把订单取消了；用户连点两次就重复操作。
方案：模型只负责提议（「要取消订单 A1001 吗？」），流程暂停；用户点确认后才真的调用商城的取消接口。LangGraph 的作用就是「暂停在这里、等用户确认、再从这里继续」，并把暂停时的状态存起来。
已经查清的商城规则：待付款、已付款未发货的订单能取消；已发货、已完成、已过期的不能（返回 409）；重复取消返回原订单、不会重复退款。所以确认流程里要处理好「确认时订单状态已经变了」这种情况。
第 6 步：演示模式 + Docker + MCP，和项目一解耦
业务：面试官问「这不就是商城的一个功能吗」，或者别人想跑起来看看，却没有你的商城。
方案：工具背后抽一层「业务系统接口」，你的商城是一种实现，内置的演示商城（假数据）是另一种，接真实商城只是换一个实现；用 Docker Compose 一条命令把 agent 和 Redis 起起来；再把业务工具做成 MCP 服务，别的 agent 客户端也能接。
第 7 步：端到端评测和链路追踪
第 4 步只测了检索；这一步测整条链路：工具选得对不对、参数对不对、该拒答时拒没拒、出处对不对、被提示注入时守不守得住。回答有没有编造，用另一个大模型来打分（LLM-as-judge）。再记录每一轮的调用链、耗时和 token 成本，出了错能查到是哪一步。
