# 检索评测

测的是检索这一步：用户问一个售后问题，应该查到的条款有没有排进前 4；政策里没有的问题，有没有被拒掉。不调大模型、不花钱，同样的代码每次跑出来都一样。

在项目根目录运行：

```powershell
.venv\Scripts\python -m evals.eval_retrieval
```

题目在 `policy_questions.jsonl`，一行一道。`expected` 是应该查到的条款编号（文件名加条款号，比如 `returns-1.1`）；空列表表示政策里没有，应该拒答。

## 看哪几个数

- **Recall@4**：应该查到的条款，有几成排进了前 4。分别算「只用向量」「只用关键词」「两个一起」，看合并到底有没有用；现在用的那种标着「当前设置」。这一项不算拒答。
- **误拒和漏拒**：拒答只看向量那一路的最高相似度。阈值定高了，政策里有的题也被拒掉（误拒）；定低了，政策里没有的题也会查出几条不相关的条款交给模型（漏拒）。脚本把 0.30 到 0.80 的阈值扫一遍，再列出两类题的最高相似度各是多少。

## 最近一次结果

2026-10-19，在 Windows 电脑上第一次运行：49 段政策，建索引 8.3 秒（包括下载约 90 MB 的模型），每道题检索约 4 毫秒。

**查得准不准（Recall@4）**

| 方式 | Recall@4 |
| --- | --- |
| 只用向量（现在用的） | 1.00 |
| 只用关键词 | 0.80 |
| 两个一起（RRF 合并） | 0.96 |

合并时丢的两题：「快递送到了，盒子是破的怎么办」（应为 `shipping-3.3`），「发票什么时候能开出来」（应为 `invoices-2.1`）。都是用户的口语和条款的书面语分词对不上，关键词那一路抓了带「快递」「发票」的条款，这些条款两路都出现，被 RRF 加了分。所以默认只用向量，见 ADR 0013。

**该拒的拒没拒**

政策里有的题，最高相似度最低是 0.569（可以指定发顺丰吗）；政策里没有的题，最高是 0.666（买完就降价了，能退差价吗）。两组有重叠。

| 阈值 | 误拒（有政策却拒了） | 漏拒（没政策却没拒） |
| --- | --- | --- |
| 0.30 到 0.40 | 0/51 | 12/12 |
| 0.45 | 0/51 | 10/12 |
| 0.50 | 0/51 | 8/12 |
| **0.55（现在用的）** | **0/51** | **6/12** |
| 0.60 | 3/51 | 1/12 |
| 0.65 | 10/51 | 1/12 |
| 0.70 | 24/51 | 0/12 |
| 0.75 | 34/51 | 0/12 |
| 0.80 | 46/51 | 0/12 |

0.55 下没拦住的 6 道：退差价（0.666）、预约周末送货（0.597）、货到付款（0.596）、补货（0.579）、两张优惠券一起用（0.557）、注销账号（0.557）。都和政策沾边，交给系统提示兜底：查到的条款没回答用户问的事，也要照实说没有规定。为什么选 0.55 见 ADR 0014。

## 已知的偏差

题和政策是同一个人写的，题目的说法会不自觉地贴近政策原文，分数会偏乐观。阈值也是在同一套题上定的，没有单独留一份题来验证。真上线要用真实用户的问题来补题。
